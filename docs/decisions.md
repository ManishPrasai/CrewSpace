# Architecture Decision Records

Check this file before proposing any infrastructure or library change.

## ADR-001: Modular monolith in Next.js
One Next.js app with feature folders. No separate API server or microservices. Reason: small team (one developer), MVP scope, simpler deployment.

## ADR-002: Supabase Postgres + RLS for tenant isolation
Relational data (workspaces, members, invites) fits Postgres. RLS enforces isolation at the database level so a bug in app code cannot leak another tenant's data.

## ADR-003: No Prisma / ORM
Queries use supabase-js with the user's session so RLS applies. An ORM with a direct connection would bypass RLS. Schema is managed with SQL migrations via Supabase CLI. Types generated with `supabase gen types`.

## ADR-004: Multi-step writes as Postgres functions
Operations that must be atomic or need row locks (create workspace, accept invite, role changes) are security definer functions with `set search_path = public` and explicit permission checks.

## ADR-005: Plan state only from Stripe webhooks
The app never sets `plan` from a redirect or client action. Webhooks are the single source of truth. Events are deduplicated via `stripe_events`.

## ADR-006: Push sent inline, no queue
At MVP scale (small workspaces) sending push inside the server action is acceptable. If workspaces grow large, move to a background job (e.g. Supabase Edge Function or queue). Not needed now.

## ADR-007: Hashed invitation tokens
Raw token only exists in the email link. Database stores SHA-256 hash. A database leak does not expose usable invite links.

## ADR-008: Email + password auth only
OAuth is out of scope for MVP to keep auth flows simple and testable.

## ADR-009: Webhook handlers re-fetch subscription state from Stripe
Subscription-related webhook events (`checkout.session.completed`, `customer.subscription.updated`) do not trust the event payload for plan/status fields. Instead the handler fetches the current subscription object from the Stripe API and writes plan/subscription_status/current_period_end from that. `checkout.session.completed` only uses the payload to link `stripe_customer_id`/`stripe_subscription_id` to the workspace, then does the same fetch. This makes the result independent of event delivery order, since Stripe does not guarantee webhooks arrive in the order the underlying events occurred.

## ADR-013: Dark mode is cookie + inline-script only, not read server-side in the root layout
Step 10 (the V2 redesign's last step) built the Appearance toggle (System/Light/Dark) as a blocking inline `<script>` in `<head>` (`src/lib/theme.ts`'s `THEME_SCRIPT`) that reads a `theme` cookie and toggles the `.dark` class on `<html>` before the browser paints anything - no flash, because head scripts run before body content renders, regardless of what the server already sent. First draft also read that same cookie *server-side* in `RootLayout` via `await cookies()`, reasoning it would help a no-JS or slow-JS visitor see the right theme on the very first paint. Caught before committing, via a real `npm run build`: doing that made `cookies()` usage in the root layout force every route in the app dynamic, including `/`, `/reset-password` and `/reset-password/update`, which had been statically prerendered since Step 1. That's a real, measurable regression (losing full static generation sitewide) to prevent a flash the inline script already prevents on its own. Removed the server-side read; `RootLayout` no longer touches cookies at all. The one accepted cost: a visitor with JS disabled always sees the light default regardless of a saved dark-mode preference - consistent with Appearance being explicitly scoped as a frontend-only, JS-dependent enhancement (05-dependencies.md section A), the same category as the keyboard shortcuts and the Copy-URL button, none of which work without JS either.

## ADR-015: Post-redesign fixes - CI build crash, Button console warnings, dark-mode-only for now
Found via the real GitHub Actions CI run for the Step 8 PR (the first full CI build after Day 8 added push, caught by the user reading the Actions log directly, not by this session) and the browser console on the running app.
1. **CI build crash: `npm run build` failed at "Collecting page data" with "Vapid public key should be 65 bytes long when decoded."** `src/features/push/send.ts` called `webpush.setVapidDetails(...)` at module scope - it validates the key's format immediately on import, and this module gets pulled in transitively by every route that can reach `createAnnouncement`, whether or not a push is ever sent. CI's `NEXT_PUBLIC_VAPID_PUBLIC_KEY` secret is apparently set but not a valid-length key, which crashed the whole build the moment that import chain was evaluated - something a local build never reproduced, since `.env.local` has a real key from Day 8's testing. Fixed by moving the call behind a lazy, memoized `ensureVapidConfigured()` invoked only inside `sendAnnouncementPush`, already wrapped in that function's existing try/catch (docs/api.md: push failures never fail the announcement action). Verified for real, not assumed: temporarily set a deliberately invalid `NEXT_PUBLIC_VAPID_PUBLIC_KEY` locally and confirmed `npm run build` now succeeds where it previously would have crashed, then restored the real key and confirmed the build still succeeds with it too.
2. **Six "Base UI: A component that acts as a button expected a native `<button>`" console warnings**, all on `/` (the marketing page). Every `<Button render={<Link href=... />}>` on that page (6 of them - both hero CTAs, both pricing-card buttons, both final-CTA buttons) defaults `nativeButton` to `true`, but a `<Link>` renders an `<a>`, not a `<button>`. Added `nativeButton={false}` at each of the 6 call sites - no other `Button`+`Link` combination exists anywhere else in the app (checked by grep, not assumed).
3. **Dark mode is removed (2026-10-16), after a first attempt at this got the user's actual instruction backwards.** First read of the user's 2026-10-15 message ("keep dark mode as default and when i tell u keep the toggle for light and dark mode") was taken as "make dark the default, hide the toggle" - ship, verify, done. The user's follow-up ("i told you to remove the dark mode") corrected that: the instruction meant stop applying dark mode at all, not make it the default. Fixed by deleting the `<script dangerouslySetInnerHTML={{ __html: THEME_SCRIPT }} />` from `RootLayout`'s `<head>` - nothing anywhere now ever adds the `.dark` class, so the site always renders light, matching how every page looked before Step 10 touched this. `src/lib/theme.ts` and `globals.css`'s `.dark` token block are left in place, unused - harmless dead code while nothing references them, and exactly the mechanism to reconnect if a real light/dark toggle is ever asked for. This supersedes point 3 above and ADR-013's framing entirely; ADR-013's substance (no server-side cookie read forcing routes dynamic) is moot now that nothing reads the cookie at all.

## ADR-016: Landing-page fidelity correction, and the app-wide font bug it surfaced
The user sent a detailed, structured correction brief after comparing the shipped `/` against the actual `C v2 - Brand & Landing.dc.html` design file and finding the implementation visually unfaithful - not a redesign request, a fidelity correction against the real source rather than an interpretation of it. Addressed by re-reading the design file's exact HTML/CSS (not relying on memory from Step 9) and, for the first time this session, verifying the result with real rendered screenshots (Playwright + headless Chromium, installed fresh - `npx playwright install chromium`) instead of curl-based text/markup checks. This is the gap that let the issues below ship in the first place: every prior "verified" check this session confirmed *content* was present in the HTML, never how it actually *rendered*.

1. **Root cause, app-wide, not marketing-page-specific: `html { @apply font-sans; }` in `globals.css` never worked, on any page, since Step 1.** `font-sans` resolves to `var(--font-geist), ...`, but `--font-geist` is only *declared* by the CSS class `next/font` puts on `<body>` in `layout.tsx` - and a CSS custom property is only visible to the element that declares it and that element's descendants, never its ancestors. `<html>` is `<body>`'s parent, so `var(--font-geist)` was undefined there, the whole `font-sans` value became invalid at compute time, and `<html>` (and everything inheriting from it, which is every element on every page) fell back to the browser's UA default - Times New Roman. This is a different, deeper bug than the one Step 1 found and thought it fixed (a naming mismatch between `--font-geist-sans` and `--font-sans`); the rename fixed the name but not the scope, and nothing caught it because no one had taken an actual screenshot of the running app until this correction pass. Fixed by moving `font-sans` from the `html` rule to the `body` rule in `globals.css` - the same element that declares `--font-geist`. Verified via `getComputedStyle` in a real headless browser, before and after: `html`/`body`/`h1` font-family all went from `"Times New Roman"` to `Geist, "Geist Fallback", ui-sans-serif, system-ui, sans-serif` on every page checked (`/`, `/login`), not just the marketing page.
2. **Hero geometry rebuilt as an actual 12-column CSS grid** (`grid-cols-12`, `gap-x-6 gap-y-10`, matching the source's `column-gap:24px; row-gap:40px` exactly) with the headline spanning the full 12 columns and the supporting paragraph placed at columns 8-12 (`col-start-8 col-span-5`) - CSS grid auto-flow puts that block on its own row below the headline, not beside it, exactly like the source. The earlier version used a two-column flexbox that squeezed the headline into roughly half the available width, which is what forced it onto three lines instead of two and made it look cramped rather than the intended "nearly full available width" composition. Also removed an extra `max-w-[1100px]` wrapper this session had added inside every section's `px-16` padding - the design file has no such inner cap anywhere in the hero, features, steps, roles, pricing or final-CTA sections; it was an unrequested constraint, not a deviation the design called for.
3. **The hero product preview was a two-layer simplification (feed + invitation toast) everywhere; it's now the full three-layer composition** (feed panel, a floating member-details popover, the invitation toast, plus the three numbered reference badges) at the design's own 1440px frame width (`min-[1440px]:`), with the simplified two-layer version still used below that as a deliberate, documented fallback - not because the design calls for it at that specific breakpoint, but because the three layers' exact pixel positions (`right:56px`, `width:980px`, etc.) are only meaningful at the width they were drawn for; extended the L3 note's own "simplifies... on tablet" allowance to cover anything narrower than exactly 1440 rather than only below 1024, since nothing between 1024 and 1439 would fit the full composition without overlap or overflow either.
4. **Nav and footer corrected against the source's exact values**: wordmark 20px/weight 600/`-0.045em` tracking (was 18px), logo mark 26px (was 24px), a real 3-column grid (`1fr auto 1fr`) for true center alignment of the pill-nav regardless of how the logo and auth-button widths differ, footer padding `96px 64px 44px` (was a flat `py-11`), wordmark tracking in the footer to match.

Not fixed in this pass (reported to the user, not silently dropped): the "Running in three steps" cards' three UI-preview boxes are still plain placeholder text, not the design's miniature form mockups - this was a deliberate, acknowledged simplification from Step 9 (three more one-off mockups for a section the brief didn't specifically call out) and the scope here was the typography/geometry/preview/nav issues the brief did name. **Built in the follow-up pass below, after the user asked for it explicitly.**

## ADR-018: Landing-page surface hierarchy - washed-out cards, root cause and fix
A third landing-page brief: the user found that cards in "Running in three steps", "Three roles" and "Free until you're more than five" (plus, on inspection, the nav pill and several surfaces inside the hero preview) were nearly indistinguishable from the page canvas - not a new design issue, a real CSS defect introduced across ADR-016/017's rebuilds.

**Root cause, found by comparing actual Tailwind class usage against `globals.css`'s token values before changing anything** (not assumed): this project defines two border tokens with very different purposes - `--border` (`#E6E5E1`, the standard card-boundary color the design source actually specifies for every outer card: step cards, the roles card, the pricing cards, the nav pill, the hero's inner panels) and `--border-subtle` (`#F1F0ED`, meant for faint internal dividers like a feed post separator, nearly invisible against the canvas by design). Every outer card in the marketing rebuild used `border-border-subtle` where the source calls for the much more visible `#E6E5E1` - a systematic mix-up, not a one-off typo, confirmed by grepping every `border-border-subtle` occurrence in the file against the exact hex the design source specifies at that element. Separately, several "inset surface" backgrounds (the step-preview inner boxes, the roles matrix body, the member-details popover's body panel, the simplified hero fallback) used `bg-muted/60` - 60% opacity of an already-pale `#F7F7F5`, which blends even closer to the `#F4F4F2` canvas than the full-opacity token does - where the source specifies that surface as fully solid. The Free pricing card compounded both problems by having no background class at all, rendering fully transparent.

Fixed by: changing every genuine outer-card border from `border-border-subtle` to `border-border` (nav pill, the three step cards, the roles card, the Free pricing card, the hero panel's two `#fff`/`#E6E5E1` surfaces); changing every `bg-muted/60` to solid `bg-muted` (step-preview boxes, roles matrix body, member-popover body panel, the sub-1440 hero fallback and its sidebar card); adding `bg-background` to the Free pricing card. Left `border-border-subtle` in place everywhere it was already correct - genuine internal dividers (feed post separators, popover header/body splits, role-table row lines) where the design source itself specifies the lighter `#F1F0ED`/`#EEEDEA` shades, confirmed per-instance against the source rather than blanket-replacing every occurrence.

Verified computationally, not just by eye: `getComputedStyle` on the step card, step-preview inset, Free card and roles card after the fix returned `rgb(255,255,255)`/`rgb(230,229,225)` (exactly `#FFFFFF`/`#E6E5E1`) for the outer cards and `rgb(247,247,245)`/`rgb(241,240,237)` for the inset surfaces - exact or near-exact matches to the source's specified values, not approximations. Re-ran the full 7-width overflow check (1920 down to 360) after the fix - still zero horizontal scroll anywhere, confirming the border/background changes didn't introduce any new sizing regressions. Console listener still reports zero errors or warnings.

## ADR-019: App shell height collapse, sidebar scroll regression, and mobile header/composer overflow

The authenticated app shell at `/w/[slug]` (shared by Feed, Members, Billing, Settings) was reported broken: the white content panel ended about halfway down the viewport with a large empty gray area below it, and the sidebar's account control wasn't positioned correctly.

**Root cause, confirmed via real `getComputedStyle`/`getBoundingClientRect` measurement in a Playwright browser authenticated with real session cookies (not assumed from reading the markup)**: `<main>` had both `min-h-screen` and `md:min-h-0` in its class list. Tailwind breakpoint prefixes are "min-width and up," not "only at this range," so `md:min-h-0` applied at *every* width ≥768px - including every desktop size - silently zeroing `min-h-screen`'s effect everywhere it mattered. Measured directly: `main`'s computed `min-height` was `"0px"` at 1440px, and the outer row collapsed to 515.75px instead of filling the ~900px viewport. The sidebar's account control uses `mt-auto` to pin itself to the bottom of the nav - a technique that only works when the nav actually has real height to push against, so it inherited the same collapse and looked "wrong" without being a separate bug.

Fixed by restructuring the shell to a flex column (`flex h-dvh flex-col`) with the sidebar/main row given `flex-1`, and `<main>` reduced to a single `min-h-0 flex-1` instead of the conflicting `min-h-screen`/`md:min-h-0` pair. Verified by re-measuring: row/main/sidebar now correctly report ~884-900px at every desktop width, and the account control sits visibly pinned at the bottom in a screenshot.

**A second bug surfaced only once the shell actually had real height**: on long pages (Settings, with the Danger Zone and Your Account sections), `<main>`'s own box grew to fit its content instead of scrolling internally, which dragged the whole document - sidebar and account control included - down past the viewport. Root cause: flex items default to `min-height: auto` (their content's intrinsic size), not `0`, at *every* level of nesting - `min-h-0` had only been applied to `<main>`, not to the row containing it, so the row refused to shrink below main's content height even though main itself was correctly constrained. Fixed by also capping the outer wrapper to `h-dvh` (a hard limit, not `min-h-dvh`'s floor-only constraint), adding `min-h-0` to the row as well as `<main>`, and changing `<main>` from `overflow-hidden` to `overflow-y-auto`. Verified via a real scroll test: before the fix, `document.documentElement.scrollHeight` (1292px) exceeded the 900px viewport and the sidebar scrolled off-screen with the page; after, `main.scrollHeight` (1274px) exceeds `main.clientHeight` (882px) and scrolls independently, while `window.scrollY` stays `0` and the sidebar/account control stay fixed in place throughout.

**A third, unrelated bug found during the mandated 7-viewport responsive sweep** (1920/1440/1280/1024/768/390/360, per the correction brief): at 390px and 360px, the page header's breadcrumb + membership-count chip and the announcement composer's placeholder text had no truncation or shrink constraints, so they wrapped across multiple lines inside fixed-height containers instead of fitting on one line - visually overlapping content. Fixed by adding `min-w-0`/`truncate`/`overflow-hidden` to `PanelHeader`'s breadcrumb slot and `shrink-0` to its actions slot; hiding the "N member(s)" text label below the `sm` breakpoint (the avatar chip alone remains); and in `AnnouncementComposer`'s collapsed trigger, truncating the placeholder span, hiding the "N" keyboard-shortcut hint below `sm` (meaningless on touch), and marking the avatar/badge/button `shrink-0` so they never wrap. Verified: all 7 viewport sizes report zero horizontal overflow and zero console errors both before and after, with before/after screenshots at 390 and 360 showing the header and composer now fit on one line.

Also verified per the correction brief's remaining requirements: Members, Billing and Settings all share this layout and were re-checked after each fix (no per-route duplication needed, all three now measure the same capped 884px `main`/`nav` height with zero console errors); a populated-feed state was seeded locally (not production data) with five announcements spanning three days plus one long multi-paragraph body, confirming day-divider grouping ("Today"/"Yesterday") and text wrapping render correctly at both 1440px and 390px, then deleted after verification; `npm run typecheck`, `npm run lint`, `npm test` (38/38) and `npm run build` all pass clean with this fix in place.

## ADR-020: Functional correctness pass - announcement refresh, /workspaces UX, account settings, shell polish

A follow-up brief shifted from visual fidelity to functional correctness: five confirmed, independent problems, investigated read-only (three parallel Explore agents plus a Plan agent validation pass) before any code changed, per every root cause below.

**Announcements didn't appear after posting without a manual reload.** Root cause: `AnnouncementFeed.tsx`'s `const [items, setItems] = useState(initialItems)` only seeds state on first mount. `createAnnouncement` already called `revalidatePath(/w/${slug})` correctly, and the Server Component page already refetched and passed fresh `initialItems` down correctly - but since `AnnouncementFeed` stays mounted across the revalidation, React ignores the new prop value for an already-initialized `useState`. Edits/deletes already worked live because `AnnouncementItem` calls `onUpdated`/`onDeleted` callbacks that mutate `items` directly, bypassing the server round-trip entirely - only create lacked an equivalent path. A repo-wide grep for the same `useState(initialX)`-without-resync shape found exactly one other hit: none - this was the only instance. Fixed by adjusting state during render (not a `useEffect`, which would commit one stale paint first) when `initialItems`'s reference changes, merging the fresh first page with any already-loaded "load more" pages deduped by id, plus a small delete-tombstone `Set` (ids are UUIDs, never reused, so it never needs eviction) so a delete can't flicker back if a concurrent revalidation's fetch still contains the row before its own `revalidatePath` lands. Verified live: created a post as Owner, confirmed it appeared with zero reload and a success toast, screenshot taken; reverted the test fixture afterward.

## ADR-021: Day 9 security audit (clean) + CLAUDE.md wording fix

Ran the audit `docs/prompts.md` section 7 specifies, against every point it names. Findings below are evidence-based (file paths/line numbers checked directly), not inferred from the docs' own claims about themselves.

**RLS coverage**: every table created across all 12 migrations under `supabase/migrations/` enables `row level security` in the same migration that creates it (`profiles`, `workspaces`, `workspace_members`, `invitations`, `announcements`, `stripe_events`, `push_subscriptions`). Tables with no client-facing policy at all (`workspace_members` insert/update/delete, `stripe_events` entirely) are documented inline as intentional default-deny, RPC/service-role-only. A pgTAP test file exists per feature under `supabase/tests/` (11 files, 90+ assertions total), with names/comments matching the coverage `docs/tasks.md` claims (e.g. `workspaces.sql` literally comments "-- Cross-tenant isolation.").

**Service-role scope**: `src/lib/supabase/admin.ts` (the service-role client) is imported in exactly two real places: the Stripe webhook handler (`src/features/billing/webhook.ts`) and the push sender (`src/features/push/send.ts`) - both allowed per CLAUDE.md. **One doc inaccuracy found**: CLAUDE.md also lists "invitation email flow" as a third allowed use site, but `src/features/invitations/actions.ts`/`email.tsx` never import `admin.ts` - that flow uses the normal RLS-scoped per-request client plus Resend directly. Not a security problem (it's *more* restrictive than the policy allows, not less), just a stale claim - fixed in this same commit.

**Secret exposure**: `src/lib/env.ts`'s client schema contains only `NEXT_PUBLIC_APP_URL`, `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`, `NEXT_PUBLIC_VAPID_PUBLIC_KEY` - all genuinely public values (anon key, VAPID *public* key). Every secret (service role key, Stripe secret/webhook secret, Resend key, VAPID *private* key) lives only in the server schema, which is a throwing `Proxy` when accessed from client code. No `NEXT_PUBLIC_`-prefixed alias of any secret found anywhere in `src/`.

**Stripe webhook**: signature verified via `stripe.webhooks.constructEvent(...)` with a 400 on failure or a missing signature header (`src/app/api/stripe/webhook/route.ts`). Idempotency via `stripe_events(id text primary key, ...)` with an insert-first pattern relying on the primary key's atomic uniqueness constraint (`src/features/billing/webhook.ts`) - not a separate check-then-insert, so no TOCTOU race window. A handler failure after the insert deletes the row so Stripe's own retry can reprocess it, intentionally and documented inline.

**Billing columns**: `workspaces`' row-level UPDATE policy would otherwise let an owner/admin update any column on their row, but `authenticated`'s column-level UPDATE grant is explicitly narrowed to `name` only (`revoke update on workspaces from authenticated; grant update (name) on workspaces to authenticated;`) - `plan`/`stripe_customer_id`/`subscription_status`/etc. stay writable only by the service-role client, which bypasses grants entirely. Same pattern already used on `profiles` (`full_name`/`avatar_url` only).

**Invitation tokens**: generated as 32 random bytes, stored only as a sha256 `token_hash` column (no raw `token` column exists in the table at all - the raw value only ever appears transiently in the email URL). The `accept_invitation` RPC re-hashes the incoming token server-side rather than trusting a client-supplied hash, checks email match / expiry / revocation / already-accepted in one combined guard, and row-locks the workspace (`select ... for update`) during the seat-limit check specifically to close the race between two concurrent accepts over-filling a free-plan workspace.

**Open redirects**: the one real client-influenced redirect site, `src/app/auth/callback/route.ts`, goes through `getSafeRedirect` (relative-path-only, rejects protocol-relative/backslash-variant/absolute targets). The invitation-accept flow doesn't take a client-supplied redirect at all - its post-accept destination is derived server-side from the workspace slug looked up in the database, not from any request parameter.

**General OWASP spot-checks**: every server action checked (announcements, members, billing, invitations, auth) calls `safeParse` before touching the database. Every `.rpc()` call site (9 total) passes its arguments as an object literal, never string-concatenated. No raw/interpolated SQL found anywhere in `src/` - all database access goes through the Supabase client or parameterized RPC calls.

**Net result: no actionable security findings.** The one fix in this pass is the CLAUDE.md wording correction above, not a code change.

## ADR-022: E2E invite-accept flow seeds its own invitation token, rather than a delivered email

Writing the Day 9 Playwright E2E suite (`tests/e2e/onboarding.spec.ts`) hit a genuine local-environment gap: `.env.local`'s `RESEND_API_KEY` is a placeholder ("invite emails will fail gracefully"), and `createInvitation` (`src/features/invitations/actions.ts`) already handles that failure gracefully by design - the invitation row is still inserted even when the email send fails, so the real "Send invite" UI/action works and is fully testable. The problem is downstream: invitation tokens are stored only as a sha256 `token_hash` (`src/features/invitations/token.ts`, `supabase/migrations/20261013140330_invitations.sql`) - by design, for the same reason passwords are hashed - so the raw token the accept flow needs exists only inside the email body, which locally never gets delivered anywhere a test could read it back.

Three options were considered: (1) seed the accept flow's token via a test-only service-role client, (2) change `src/features/invitations/email.tsx` to route through the local Mailpit SMTP in dev (mirroring how Supabase Auth's own emails already work locally) so the real email becomes readable, or (3) drop the accept/member-cannot-post coverage from this pass entirely. Asked the user directly rather than guessing, since each has different tradeoffs (test realism vs. production-code changes vs. reduced coverage) - chose option 1.

**Implementation**: `tests/e2e/helpers/db.ts` builds its own service-role client (deliberately *not* importing `src/lib/supabase/admin.ts` - that import stays restricted to the Stripe webhook and push sender per CLAUDE.md; this is a separate client, scoped to `tests/e2e/`, never reachable from a request) and inserts a second invitation row with a token the test generates and hashes itself, using the exact same algorithm as `generateInvitationToken()`. The real "Send invite" UI/action is still exercised once per test run for coverage of the create side; only the accept side's starting token is test-seeded. From that point on, the accept flow is 100% real: the genuine `/invite/[token]` page, the genuine `accept_invitation` RPC (email match, expiry, single-use, seat-limit row lock all still enforced for real), and the genuine post-accept UI state (including the "member cannot post" assertion, which checks the real composer's absence in the real DOM).

This is a deliberate, documented compromise specific to the local no-real-email-service environment, not a shortcut - the thing that's actually unverified this way is "does a real Resend-delivered email contain a working link," which is a Resend/email-template concern, not an application-logic concern, and is out of scope for Day 9's E2E pass regardless of how the token arrives.

## ADR-023: Two real accessibility bugs found by the new axe-core suite, plus two confirmed false positives

Running the new E2E suite's `axe-core` checks for the first time surfaced four findings. Two were real, confirmed by a second independent method before fixing anything; two were false positives, confirmed the same way before dismissing them - neither direction was taken on axe's word alone.

**Real bug 1 - `/login`'s password field had no accessible label at all.** `LoginForm.tsx` hand-writes its own `<label htmlFor="password">` (bypassing the `Field` component, which auto-associates via `cloneElement`, because this one field also needs a "Forgot password?" link inline with the label) - but never passed a matching `id="password"` to `PasswordInput`, so the label and input were never actually associated. `PasswordInput` already accepts an `id` prop for exactly this case; the fix is the one missing prop. Grepped every other `PasswordInput` call site (`SignUpForm.tsx`, `UpdatePasswordForm.tsx`) - both go through `Field`, which handles this automatically, so `LoginForm.tsx` was the only affected site.

**Real bug 2 - four links distinguished from surrounding text by color alone, and the color didn't even meet the fallback contrast requirement.** `text-brand-ink hover:underline` (teal, underlined only on hover) on the "Sign up"/"Log in" cross-links on the auth pages, the sidebar's "Upgrade to Pro" link, and the login form's "Forgot password?" link - measured contrast against the surrounding muted-gray text was 1.61:1, well under WCAG 1.4.1's 3:1 minimum for a color-only distinction, and with no underline by default there was no non-color distinguishing feature either. Fixed by making the underline permanent (`underline` instead of `hover:underline`) on all four - a non-color cue that resolves the violation without touching the color token, and grepped for every other `text-brand-ink` usage in `src/` to confirm nothing else matched this exact "a `<Link>`/`<a>` inside a paragraph of surrounding body text" pattern (the remaining hits are status badges, role chips and decorative marketing spans, not links competing with body text).

**False positive 1 - `AccountMenu`'s trigger button.** axe's `label-content-name-mismatch` rule flagged `aria-label="Account menu"` not containing the visible "EO"/"OU" initials rendered inside it. Verified via Playwright's own accessibility snapshot (which implements the real W3C accessible-name computation) that the rendered tree is already correct: `button "Account menu": generic [aria-hidden]: EO` - the initials are properly excluded from the accessible name by their own `aria-hidden="true"` (`src/components/app/Avatar.tsx`). This specific axe rule checks raw DOM text content rather than the full accname algorithm, and is a documented false-positive class for icon buttons with `aria-hidden` decorative content. Disabled just this one rule for the E2E suite's scans (`tests/e2e/onboarding.spec.ts`'s `scan()` helper), with the reasoning recorded inline - not disabled globally, not silently ignored.

**False positive 2 - transient color-contrast failures mid-dialog-close-animation.** The invite dialog (`InviteDialog.tsx`) closes itself on success; its ~100ms CSS exit transition was still mid-fade when a scan ran immediately after the invite succeeded, and axe caught the dialog's text at a near-transparent animation frame (foreground color computed as `#fbfbfb`/`#fdfdfc` against a white background) and reported it as a static contrast failure. Confirmed by re-running after adding a short wait for the transition to finish - zero violations, consistently, across multiple runs. Not a real accessibility bug (WCAG doesn't require every intermediate animation frame of a closing modal to meet contrast ratios, only the persisting static states) - just a test-timing issue, fixed in the test, not the app.

Verified: `npm run typecheck && npm run lint && npm test` (38/38) all pass; `npm run test:e2e` passes cleanly across 5+ consecutive runs after the timing fix (previously flaky ~1-in-3 before it); a standalone axe scan of `/login` and `/signup` outside the E2E suite confirms zero violations post-fix.
